# F10.5 – Console contract (shared-database interface for a separate front end)

## Goal
Let a separately built console (React + a Node middleware, built later in F14's slot) drive the
agent while sharing **only the Postgres database** with this repo. Define that database as the
contract: read-only views for reading, one request table for writing, and a relay in the worker
that turns requests into the same actions the API performs today.

## In scope
- Alembic migration `0006`:
  - schema `console`; role `console_app` (LOGIN, password from `CONSOLE_DB_PASSWORD`, created if absent).
  - `cases.evidence JSONB` (nullable), written by `complete` / `mark_awaiting_review` so an analyst
    can see the evidence a verdict cites (today it lives only in the LangGraph checkpoint).
  - table `console.requests` (the outbox): `request_id uuid PK` (generated by the console, so a retry
    is idempotent), `kind` (`investigate` | `decision`), `alert_id`, `case_id`, `payload jsonb`,
    `requested_by text`, `status` (`pending` | `applied` | `rejected`), `result jsonb`,
    `created_at`, `processed_at`. A trigger runs `pg_notify('console_requests', request_id)` on insert.
  - views: `console.v_alert_queue` (alert, rule, score, case status/outcome/risk score, newest first)
    and `console.v_case_detail` (alert, case, verdict, evidence, sar_draft, escalation_reason,
    decision, error), `console.v_requests` (a requester's own request status and result).
  - grants: `console_app` has `USAGE` on schema `console`, `SELECT` on the views, `INSERT` on
    `console.requests`. Nothing on `public` tables (views run with their owner's rights).
- `app/services/case_commands.py`: `start_investigation(alert_id)` and `record_decision(...)`, moved out
  of `app/api/routes.py` so the API and the relay share one code path. Behaviour of the API is unchanged.
- `app/worker/console_relay.py`: a task in the worker process. It wakes on `LISTEN console_requests`
  and also polls (default 5 s), claims rows with `FOR UPDATE SKIP LOCKED`, applies them via
  `case_commands`, sends the SQS message (`investigate` or `resume`), then marks the row `applied`
  or `rejected` with a reason (unknown alert, case not `awaiting_review`, conflicting decision).
- Settings in `app/config.py` and `.env.example`: `CONSOLE_DB_PASSWORD`, `CONSOLE_RELAY_ENABLED`,
  `CONSOLE_RELAY_POLL_SECONDS`.
- `docs/console-contract.md`: the contract for the console team (views, columns, request payloads,
  status meanings, example SQL). This is the only document the console project needs.

## Out of scope
The console itself (React/Node), its login and users (the console owns those), RBAC on the Python
side (F11), per-request SSE (the console polls `v_case_detail`; Redis SSE stays internal),
an `evidence` table (JSONB on `cases` is enough for now), "request more info" decisions.

## Interfaces
- Request payloads:
  - `investigate`: `{kind:"investigate", alert_id}`
  - `decision`: `{kind:"decision", case_id, payload:{decision:"approve"|"reject", notes}}`; the analyst
    is `requested_by`.
- Status flow: `pending -> applied | rejected`. `result` holds `{case_id, case_status}` on success,
  `{error, code}` on rejection (`code` mirrors the API: 404 / 409).
- The `decisions` and `audit_log` rows are still written only by Python (`record_decision`), with
  `audit_log.actor` = `requested_by` and detail `{via:"console", request_id}`. The console never
  writes them directly, so the invariants from F08 cannot be bypassed.
- Delivery is at-least-once and idempotent: the SQS message is sent after the DB commit; a crash before
  marking `applied` re-runs the request, and F08 already makes a repeated decision/resume a no-op.

## Acceptance criteria
- Migration 0006 upgrades and downgrades cleanly (role, schema, views, trigger removed on downgrade).
- `console_app` can `SELECT` the views and `INSERT` into `console.requests`; it gets `permission denied`
  on `alerts`, `cases`, `decisions`, `audit_log` and on `UPDATE`/`DELETE` of `console.requests`.
- An `investigate` request creates the case once and enqueues it; a duplicate `request_id` is rejected by the
  primary key; two requests for the same alert yield one case.
- A `decision` request on an `awaiting_review` case records the decision and audit row and resumes the
  graph; on any other status it is marked `rejected` with code 409 and changes nothing.
- Replaying an already-applied request (simulated crash before the status update) creates no second
  decision, audit row or case.
- Two relays running at once never apply the same request twice (`SKIP LOCKED`).
- With `CONSOLE_RELAY_ENABLED=false` the worker runs exactly as in F10.
- `v_case_detail` shows evidence for a completed and an awaiting-review case.
- The existing API tests still pass unchanged; ruff, mypy and pytest pass (DB tests skip without Postgres).
